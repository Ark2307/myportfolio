Consensus algorithms are the beating heart of distributed systems. Every time a cluster of machines needs to agree on a value — a configuration change, a transaction commit, a leader — they run a consensus protocol. Raft was designed with one explicit goal: **understandability**.

## The Problem: Split Brain

Imagine three nodes: `Node A`, `Node B`, and `Node C`. The network partitions and A loses contact with B and C. Who is the leader now?

If both sides elect their own leader, you get a **split-brain** scenario — two leaders accepting conflicting writes. The data is now permanently diverged.

Raft prevents this with a simple invariant: **a leader can only be elected if it gets votes from a majority quorum**.

## Leader Election

Each node starts as a **Follower**. Followers expect periodic heartbeats from the current leader. If no heartbeat arrives within the **election timeout** (150–300ms randomized), the follower becomes a **Candidate** and starts an election:

1. Increments its `currentTerm`
2. Votes for itself
3. Sends `RequestVote` RPCs to all other nodes

A node grants a vote if:
- The candidate's term is at least as large as its own
- It hasn't already voted in this term
- The candidate's log is at least as up-to-date as its own

The randomized timeout is elegant: nodes don't all wake up simultaneously, so one node typically starts the election first and wins before others even try.

## Log Replication

Once elected, the leader accepts client requests and appends them to its log. It then sends `AppendEntries` RPCs to all followers. An entry is **committed** once a majority acknowledges it.

```
Leader:  [1: SET x=1] [2: SET y=2] [3: DEL z] ← new entry
Follower A: [1: SET x=1] [2: SET y=2]         ← replicating...
Follower B: [1: SET x=1] [2: SET y=2] [3: DEL z] ← confirmed
```

The commit index advances only when the majority confirms. The leader then notifies followers of the new commit index in the next heartbeat.

## Safety Guarantee: The Log Matching Property

Raft guarantees that if two logs have the same index and term for an entry, all preceding entries are identical. This is enforced by the `prevLogIndex` and `prevLogTerm` fields in `AppendEntries` — a follower rejects the entry if its own log doesn't match at the previous position.

## Cluster Membership Changes

Adding or removing nodes is dangerous. If you go from 3 to 5 nodes instantly, you may have two different majorities operating simultaneously. Raft handles this with **joint consensus** — a two-phase approach where the cluster temporarily operates under both the old and new configuration.

## When Raft Falls Short

Raft is not the right tool when:
- You need **Byzantine fault tolerance** (Raft trusts all nodes; use PBFT or Tendermint instead)
- You need **geo-distributed** low-latency writes (Raft requires majority round trips; consider EPaxos)
- Log compaction overhead is unacceptable (Raft's snapshotting must be carefully tuned for write-heavy workloads)

## Real Systems Using Raft

- **etcd** — Kubernetes cluster state
- **CockroachDB** — per-range consensus
- **TiKV** — distributed KV store backing TiDB
- **Consul** — service discovery and configuration

Understanding Raft deeply means understanding the tradeoffs of every distributed database you'll use. The simplicity is the point — it's auditable, implementable, and debuggable.
